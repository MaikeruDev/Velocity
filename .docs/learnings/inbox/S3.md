## Supabase Auth nimmt Loopback-Rücksprünge ohne Allow-List an (Plan 011 S3, Desktop-Login)

GoTrue `IsRedirectURLValid`: Ist der Host eine IP, zählt nur `ip.IsLoopback()` — `http://127.0.0.1:<jeder Port>/<jeder
Pfad>?<jede Query>` ist ohne Eintrag in den Redirect URLs gültig (RFC 8252). Alles andere muss in der Allow-List stehen,
sonst fällt GoTrue STILL auf die Site-URL zurück (kein Fehler beim Authorize). **Prüfen ohne Login:** `GET
/auth/v1/authorize?provider=discord&redirect_to=…` mit `redirect: 'manual'` → `state` aus der Discord-Location →
`GET /auth/v1/callback?state=<uuid>&error=access_denied&error_description=probe` → die Location ist der gespeicherte,
geprüfte Rücksprung (live 06.11.: 127.0.0.1 samt eigenem `?state` kam an, fremde Domain → Site-URL).

## GoTrue-OAuth-`state` ist eine UUID, kein JWT mehr — Authorize verrät nicht, ob der Rücksprung erlaubt ist (Plan 011 S3)

Früher stand der geprüfte `referrer` im JWT-`state`; heute ist `state` die ID der `flow_state`-Zeile (serverseitig).
Das `redirect_to` in der Discord-URL ist nur das durchgereichte Roh-Argument (GoTrue hängt unbekannte Query-Parameter an
den Provider-Link), nicht der geprüfte Wert. Ein "Redirect nicht erlaubt"-Fehler lässt sich vor dem Login also nicht
erkennen — am Desktop meldet ihn nur die Zeitüberschreitung (Text nennt den Grund).

## Allow-List vergleicht MIT Query — eigener `?state=` braucht `/**`-Einträge (Plan 011 S3)

`IsRedirectURLValid` matcht die URL ohne Fragment, aber mit Query (auch der Kommentar zu `appendPkceFlowIdToRedirects` in
auth-js sagt das). Ein exakter Eintrag `http://127.0.0.1:47823/auth/callback` passt auf `…/auth/callback?state=…` NICHT.
Falls je nötig: `http://127.0.0.1:47823/**` usw. GoTrue erhält die eigene Query beim Anhängen von `code`/`error`
(`prepPKCERedirectURL`: `u.Query()` + `Set`).

## supabase-js 2.119: PKCE-Verifier liegen unter mehreren Schlüsseln — eigener Storage nur per EXAKTEM Schlüssel (Plan 011 S3)

Seit dem "slot ring" schreibt auth-js `<storageKey>-code-verifier`, `<storageKey>-flow-<id>-code-verifier` und
`<storageKey>-flows-code-verifier`; die Sitzung selbst steht unter `<storageKey>` (= `sb-<ref>-auth-token`). Ein Adapter,
der die Sitzung verschlüsselt, darf nur `key === storageKey` umleiten — ein Präfix-Vergleich finge die Verifier mit ein.
`signInWithOAuth` liefert `flowId`; `exchangeCodeForSession(code, { flowId })` nimmt dann genau den Verifier dieses Flows
(ohne flowId: der zuletzt gespeicherte). `skipBrowserRedirect` hängt bei `signInWithOAuth` KEIN `skip_http_redirect` an
(nur bei linkIdentity) — die URL ist im System-Browser direkt öffnbar.

## Electron 45: `safeStorage` synchron ist veraltet — async und Schreiben in Reihe (Plan 011 S3)

`encryptString`/`decryptString`/`isEncryptionAvailable` sind deprecated; `encryptStringAsync`, `decryptStringAsync()`
(→ `{ result, shouldReEncrypt }`), `isAsyncEncryptionAvailable()`. Weil supabase-js Refresh/Abmelden schnell
hintereinander schreibt, im Hauptprozess eine Promise-Kette (sonst überholt ein älterer Stand den neueren).

## Ein Callback, dann zu: die zweite Verbindung stirbt vor dem Lesen (Plan 011 S3)

Nach der ersten gültigen Antwort `server.close()` + `closeAllConnections()` (auf `res 'close'`). Gemessen 60/60: eine
zweite, VORHER verbundene Anfrage wird getrennt, bevor der Handler sie sieht. Der 410-Zweig ("schon abgeschlossen") ist
damit reine Absicherung; Tests auf "zweiter Callback ignoriert" müssen Verbindungsabbruch ODER 410 erlauben. Gegenprobe
für state/Host/`redirect_to` (Prüfung aus → Test rot) funktioniert dagegen deterministisch.

## Electron-Logik testbar halten: kein `import … from 'electron'` in Dateien, die Vitest lädt (Plan 011 S3)

`require('electron')` liefert in Node nur den Binary-Pfad — benannte Importe scheitern. Reine Logik (`electron/auth.ts`,
`session.ts`, injizierte Verschlüsselung/`openExternal`) getrennt von der Verdrahtung (`authModule.ts` mit `shell`,
`safeStorage`); `import type` aus `modules.ts` ist unkritisch (wird entfernt). Ohne Browser testbar am echten Electron:
ein `--dev`-only-Schalter (`--auth-no-browser`) legt die geprüfte URL in den Hauptprozess (`app.evaluate`).
